## 判断

[OKF](/formats/okf) は採用に値する。ただし全社ドキュメント基盤の移行先としてではなく、**リポジトリ単位の「コードが語れないこと」の置き場**として始める。

## 根拠

### 採る理由

規格の要求が極小である。必須は `type` 一つで、消費側は未知のフィールドも未知の型もリンク切れも拒否してはならない。つまり導入の失敗コストが低い。合わなければ、残るのは普通の Markdown ディレクトリであって、専用形式に閉じ込められた資産ではない。

Git 運用にそのまま乗る。PR レビュー、diff、blame、CODEOWNERS がすべて機能する。知識の手入れをソフトウェア開発と同じ営みに落とせる。

### 採る範囲を絞る理由

コミュニティのベンチマークが示した結果が示唆的だった。12 エージェント、6 問、盲検採点で、バンドルのある側は正答率 85%（22/26）、無い側は 77%（20/26）。一方で消費トークンは 5% 増えており、「三千行ではなく三ファイルを読む」という触れ込みは、この規模のリポジトリでは成立しなかった。

意味があったのは「なぜ」を問う質問（ADR にしか書かれていない意思決定の理由）であり、負けたのは「どこを直すか」を問う質問だった。要約された概念が、ソースにあった詳細を落としていたためである。

ここから引く線は明確で、**コードを読めば分かることを概念に書いても測定可能な利得はない**。書くべきは、定数がなぜその値なのか、その設計をなぜ選ばなかったのか、といったコードが語れない情報に限る。

### 保留する理由

仕様が意図的に解いていない問題が、組織展開の障害になりうる。アクセス制御は形式の外、つまりバンドルを渡すか渡さないかでしか表現できない。機密情報を含む知識を部分的に共有する運用は、現状の仕様では組めない。

削除の表現も無い。消された概念と、まだ書かれていない概念が、消費側から区別できない。監査が要る領域では、この前提を受け入れられるか事前に確認する必要がある。

## 最初の一歩

1. リポジトリに `.okf/` を切り、[CI 検証](/runbooks/validate-okf-bundle-in-ci)を先に通す。空でも通る状態を作ってから書き始める。
2. 書く対象を `decisions/`（なぜそうしたか）と `runbooks/`（障害時に何をするか）に限定する。スキーマやコード構造は書かない。
3. `CLAUDE.md` に「作業前に `.okf/` を参照、作業後に得た知見を書き戻す」を一行足す（[AGENTS.md / CLAUDE.md](/formats/agents-md) 参照）。書き戻しは PR レビューを経る。
4. 1 ヶ月運用して、概念が増えているか、参照されているかを見る。増えないなら形式の問題ではなく書く習慣の問題なので、そこで打ち切る。
